# 부하 테스트 가이드

이 문서 하나로 준비부터 발표까지 끝난다. 명령은 복사해서 그대로 쓴다.

- **재는 것**: 운영 ECS(1 vCPU / 3GB) 기준으로 이 서비스가 동시 몇 명을 감당하는가, 개선 후 얼마나 나아졌는가
- **최종 산출물**: 아래 두 문장과 그 근거 그래프

> 개선 전에는 동시 75명에서 무너졌는데, 개선 후에는 150명까지 버팁니다.
> 같은 동시 150명 조건에서 응답이 4.3초에서 0.6초로 줄었고 처리량은 1.6배가 됐습니다.

---

## 0. 고정값 — 이 표가 기준이다

**실행자가 바꾸는 것은 `TESTID` 하나뿐이다.** 나머지를 하나라도 바꾸면 다른 사람 결과와 비교할 수 없다.

### 환경

| 항목 | 고정값 |
| --- | --- |
| 대상 | `BASE_URL=http://localhost:8080` (운영·공용 서버 금지) |
| 스프링 기동 | CPU 1개 핀 + `-Xmx768m -XX:ActiveProcessorCount=1` |
| PostgreSQL · Redis | Docker, 코어 제한 없음 |
| 파이썬 (AI 시나리오만) | `AI_STUB_MODE=true` `AI_STUB_DELAY_MS=10000` `AI_STUB_JITTER_MS=2000` |
| DB 데이터 | 전/후 사이에 바꾸지 않는다 |
| 계정 | **15개** (프리랜서 8 / 클라이언트 7) |

### 부하

| 항목 | 고정값 |
| --- | --- |
| 목표 VU | **150** (S3 AI 시나리오만 30) |
| 한계점 측정 | `PROFILE=stress` · `DURATION=2m` · `RAMP=30s` — 약 13분 |
| 전/후 비교 | `PROFILE=load` · `DURATION=3m` · `RAMP=30s` — 약 4분 |
| 합격 기준 | 기본값 그대로 두고 **명령에 넣지 않는다** |

기본 합격 기준: 비로그인 p95 500ms / 조회 1000ms / 쓰기 1500ms / AI 30000ms / 실패율 1%.
명령에 안 쓰는 것 자체가 통일 장치다. 쓰기 시작하면 사람마다 달라진다.

### 시나리오 (세트를 바꾸면 THINK_MS 도 같이 바뀐다)

| 세트 | APIS | THINK_MS | VU |
| --- | --- | --- | --- |
| **S1 공개** | `meta_skills,meta_jobroles,terms_list,home_summary` | `4500` | 150 |
| **S2 폴링** | `me,notifs_unread,chat_unread,negos_waiting,chatrooms,notifs` | `7000` | 150 |
| **S3 AI** | `ai_chatbot` | `1000` | 30 |

대표 지표는 **S2** 다. S1 은 캐시 개선을 보여줄 때, S3 는 AI 서버 용량을 볼 때 쓴다.

### 실행 이름

```
<세트>-<프로파일>-<상태>        예: s2-load-before, s2-load-after, s2-stress-before
```

같은 이름이면 리포트를 덮어쓴다. `reports/*.json` 은 비교에 쓰이니 실행자가 보관한다.

## 1. 용어

| 말 | 뜻 |
| --- | --- |
| **VU** | 동시 접속자 수. 가입자 수가 아니다. `VUS=150` 은 "지금 화면을 켜 놓고 쓰는 사람 150명" |
| **반복(iteration)** | VU 한 명이 도는 한 사이클. 이 스크립트에서는 **고른 API 를 전부 한 번씩** 호출하는 것 |
| **생각 시간(THINK_MS)** | 반복 사이에 쉬는 시간. 0 이면 서버가 아니라 내 PC 한계를 재게 된다 |
| **증감(RAMP)** | 인원을 서서히 채우는 시간. 한꺼번에 넣으면 순간 충격인지 진짜 한계인지 구분이 안 된다 |
| **처리량(req/s)** | 서버가 초당 처리한 건수. **서버의 능력치** |
| **p95** | 100건 중 95번째로 느린 응답. 평균은 보지 않는다 — 5%가 10초씩 기다려도 평균은 멀쩡해 보인다 |
| **포화** | 처리량이 더 안 늘고 대기 줄만 길어지는 상태 |
| **한계점(무릎)** | 포화가 시작되는 지점. **감당 가능한 인원은 무릎으로 찍힌 계단의 앞 계단이다** |
| **합격 기준(threshold)** | 사전 약속한 지연·실패율 상한. 넘으면 k6 가 종료 코드 99 로 끝난다(실행 실패가 아니다) |
| **스텁** | 실제 Gemini 대신 형태만 같은 가짜 응답. 쿼터 소진과 비용을 막는다 |

## 2. 준비

### 2-1. 스프링을 1 vCPU 로 묶어서 띄운다

**이걸 빼면 이후 숫자가 전부 무의미하다.** 내 PC 는 코어가 많아 150명을 여유롭게 받아내고, 그렇게 나온 한계는 ECS 가 아니라 내 PC 의 한계다.

```bash
./gradlew bootJar
```

```bash
$p = Start-Process java -ArgumentList '-Xmx768m','-XX:ActiveProcessorCount=1','-jar','build/libs/app.jar' -PassThru; $p.ProcessorAffinity = 1
```

| 옵션 | 하는 일 |
| --- | --- |
| `ProcessorAffinity = 1` | CPU 0 하나만 쓰게 묶는다 |
| `-XX:ActiveProcessorCount=1` | JVM 이 스스로 1코어라고 인식하게 한다. 없으면 GC 스레드 수가 실제 코어 수대로 잡혀 ECS 와 다르게 동작한다 |
| `-Xmx768m` | ECS 실제 힙 크기. Dockerfile 에 힙 옵션이 없어 3GB 의 25% 인 768MB 만 쓰고 있다 |

PostgreSQL 과 Redis 는 묶지 않는다. ECS 도 RDS 를 별도 장비로 쓰므로 묶지 않는 쪽이 실제와 가깝다.

```bash
docker compose up -d
```

### 2-2. 테스트 계정 15개

이 서비스는 로그인하면 그 계정의 이전 세션을 끊는다. 스크립트가 계정당 한 번만 로그인해 이 문제를 피하지만, 계정이 너무 적으면 모든 VU 가 같은 사용자 데이터를 보게 되어 캐시·락 영향이 실제와 달라진다.

- 개수도 고정해야 한다. 실행마다 다르면 비교 페이지가 "조건이 다르다"고 경고한다
- 비밀번호에 `:` 를 쓸 수 없다. 계정 형식이 `이메일:비밀번호:역할` 이라 구분이 깨진다
- **실제 사용자 계정을 쓰지 않는다.** 비밀번호가 명령줄과 셸 히스토리에 평문으로 남는다

> 비밀번호를 틀린 채로 재실행하지 않는다. 로그인 실패가 IP 기준 1시간에 20회를 넘으면 그 IP 가 **2시간 차단**되어 그날 테스트가 끝난다. 스크립트는 한 실행에서 3회 실패로 멈추지만, 재실행을 반복하면 서버 쪽 카운터가 누적된다.

### 2-3. 파이썬 (AI 시나리오를 돌 때만)

지연을 10초로 고정한 이유가 있다. 챗봇 1회는 스텁을 2번 호출하므로(관련성 임베딩 + 답변 생성) 실제 응답이 약 20~24초가 된다. 20초로 두면 40초가 되어 기본 기준 `P95_AI=30000` 을 무조건 넘긴다.

### 2-4. k6

```bash
k6 version
```

없으면 `winget install k6`.

## 3. 생각 시간이 세트마다 다른 이유

한 반복에서 고른 API 를 전부 호출하므로, API 개수가 바뀌면 같은 `THINK_MS` 라도 부하가 몇 배씩 달라진다.

```
VU 1개의 초당 요청 = n / (n × R + Z)      n = API 개수, R = 응답시간, Z = 생각시간
```

사용자 1명이 초당 0.85건(1.2초에 1건)을 만들도록 맞춘 값이 0절의 표다. API 6개를 고른 채 `THINK_MS=1000` 으로 돌리면 VU 1명이 4.6 req/s 를 만들어서, 150명이면 690 req/s 가 나간다. 1 vCPU 천장(50~100 req/s)의 7배다.

표준 세트 세 개 모두 **ID 가 필요한 API 와 쓰기 API 를 뺐다.** ID 필요 API 는 계정이 2개 이상이면 첫 계정 외에는 권한 오류를 받아 숫자가 오염되고, 쓰기는 DB 상태를 바꿔서 다음 실행과 비교가 안 된다.

## 4. 실행 절차

### 0단계 — 설정 확인 (30초)

계정과 주소가 맞는지만 본다. 부하가 아니다.

```bash
k6 run k6/main.js -e BASE_URL=http://localhost:8080 -e ACCOUNTS='<계정 1개>' -e APIS='me,notifs_unread' -e PROFILE=smoke -e TESTID=smoke
```

`PROFILE=smoke` 는 VU 1 · 30초 고정이라 VU 설정을 줘도 무시된다.

### 1단계 — 한계점 측정 (13분, 개선 전에 한 번)

```bash
k6 run k6/main.js -e BASE_URL=http://localhost:8080 -e ACCOUNTS='<15개 계정>' -e APIS='me,notifs_unread,chat_unread,negos_waiting,chatrooms,notifs' -e PROFILE=stress -e VUS=150 -e DURATION=2m -e RAMP=30s -e THINK_MS=7000 -e TESTID=s2-stress-before
```

계단은 38 → 75 → 113 → 150 → 225명이다. 첫 계단은 워밍업이니 수치가 나빠도 무시한다.

**여기서 고정 VU 값을 확정한다.**

| 결과 | 조치 |
| --- | --- |
| 무릎이 75명 이전 | 이후 모든 실행의 VU 를 **75** 로 낮춘다 |
| 무릎이 75~150명 사이 | **150** 확정. 그대로 간다 |
| 225명까지 안 무너짐 | **300** 으로 올려 다시 측정한다 |

확정한 값을 0절 표에 적어 두고 팀 전체가 같은 값을 쓴다.

### 2단계 — 개선 전 기준선 (4분)

VU 를 고정하고 재는 본 측정이다.

```bash
k6 run k6/main.js -e BASE_URL=http://localhost:8080 -e ACCOUNTS='<15개 계정>' -e APIS='me,notifs_unread,chat_unread,negos_waiting,chatrooms,notifs' -e PROFILE=load -e VUS=150 -e DURATION=3m -e RAMP=30s -e THINK_MS=7000 -e TESTID=s2-load-before
```

캐시 개선을 할 계획이면 공개 API(S1)도 같은 방식으로 받아 둔다. 이쪽 그래프가 더 선명하다.

```bash
k6 run k6/main.js -e BASE_URL=http://localhost:8080 -e APIS='meta_skills,meta_jobroles,terms_list,home_summary' -e PROFILE=load -e VUS=150 -e DURATION=3m -e RAMP=30s -e THINK_MS=4500 -e TESTID=s1-load-before
```

### 3단계 — 코드를 고친다

Grafana 에서 병목을 먼저 확인하고 손댄다. k6 는 "느려졌다"까지만 알려준다.

| 볼 것 | 의미 |
| --- | --- |
| `tomcat_threads_busy` vs `config_max` | 처리 스레드 부족 |
| `hikaricp_connections_pending` | 0 을 넘으면 DB 커넥션 대기. **1 vCPU 에서 풀 10 은 적정하니 먼저 손대지 않는다** |
| JVM 힙 · GC 시간 | 힙 압박. Dockerfile 에 `-XX:MaxRAMPercentage=70` 이 후보다 |

### 4단계 — 개선 후 측정

**`TESTID` 만 바꾼다. 다른 값은 하나도 건드리지 않는다.**

```bash
k6 run k6/main.js -e BASE_URL=http://localhost:8080 -e ACCOUNTS='<15개 계정>' -e APIS='me,notifs_unread,chat_unread,negos_waiting,chatrooms,notifs' -e PROFILE=load -e VUS=150 -e DURATION=3m -e RAMP=30s -e THINK_MS=7000 -e TESTID=s2-load-after
```

한계점이 얼마나 올라갔는지도 보려면 1단계 명령을 `TESTID=s2-stress-after` 로 한 번 더 돌린다.

### 5단계 — 비교

`k6/compare.html` 을 브라우저로 열고 `reports/s2-load-before.json` 과 `reports/s2-load-after.json` 을 넣는다. 조건이 어긋나면 경고가 뜬다.

## 5. 결과 읽기

실행이 끝나면 세 개가 남는다.

| 출력 | 위치 |
| --- | --- |
| 텍스트 요약 | 터미널 |
| HTML 리포트 | `k6/reports/<TESTID>.html` |
| JSON | `k6/reports/<TESTID>.json` — 비교 페이지 입력용 |

**반드시 `Pairing-backend` 폴더에서 실행한다.** 리포트를 상대경로로 저장한다.

### 한계점 표 (stress 결과)

```
동시접속   요청     p95        앞구간대비   실패율
    38명    3820     78.4ms          -     0.00%
    75명    7410    124.0ms       1.6배     0.00%
   113명   10680    268.2ms       2.2배     0.00%   ← 한계
   150명    3390      4.31s      16.1배     0.42%
```

- `앞 구간 대비` 가 갑자기 튀는 줄이 무릎이다. 판정 기준은 지연 2배 이상 또는 실패율 1% 이상
- **감당 가능한 인원은 무릎의 앞 계단이다.** 위 표는 "동시 75명" 이라고 말한다
- 요청 수가 줄어드는 것도 신호다. 113명 10,680건 → 150명 3,390건이 포화의 증거다

### 고정 VU 비교 (load 결과)

| | 개선 전 | 개선 후 |
| --- | --- | --- |
| 동시 접속 | 150명 | 150명 (고정) |
| 실행 시간 | 3분 | 3분 (고정) |
| 처리한 요청 | 21,000건 | 34,000건 |
| p95 | 4.31s | 0.62s |

**처리한 요청 수가 다른 것은 정상이다.** VU 와 시간을 고정하면 반복 횟수는 서버 속도에 따라 달라진다. 셋 중 둘만 고정할 수 있고, 늘어난 요청 수는 조건이 아니라 개선의 결과다.

### 주의해서 읽을 것

- 리포트 헤더의 초록색 **"기준 통과" 를 그대로 믿지 않는다.** 요청이 0건인 그룹도 통과로 표시된다. 그룹별 호출 건수를 같이 본다
- **"제외된 항목"을 반드시 읽는다.** 데이터가 없어 빠진 API 는 측정되지 않은 것이다
- p95 가 비현실적으로 좋으면 403·404 를 재고 있을 수 있다. 실패율부터 확인한다
- 리포트 숫자는 **클라이언트가 기다린 시간**이다. 네트워크와 대기열이 포함돼 있다. 서버 처리 시간은 Grafana 를 같은 시간대로 맞춰 본다

## 6. 발표 문장

운영 스펙을 앞에 붙여야 "내 노트북에서 잰 값"이 아니라 **실제 서버 용량**으로 읽힌다.

> ECS 1 vCPU 기준으로, 개선 전에는 동시 75명에서 무너졌는데 개선 후에는 150명까지 버팁니다.
> 같은 동시 150명 조건에서 p95 응답이 4.3초에서 0.6초로 줄었고, 3분간 처리량은 21,000건에서 34,000건으로 늘었습니다.

## 7. 하지 않는 것

| | 이유 |
| --- | --- |
| 운영·공용 서버 대상 실행 | `BASE_URL` 은 localhost 만 쓴다. develop 과 main 이 같은 ECS 서비스를 가리킨다 |
| 쓰기 API(`chat_send` 등)와 `ai_embed_fl` | 데이터가 실제로 남는다. `ai_embed_fl` 은 프리랜서 1번의 이력서 벡터를 더미로 덮어써서 그 계정의 매칭 결과를 조용히 망가뜨린다 |
| ID 가 필요한 API + 계정 2개 이상 | 첫 계정으로만 ID 를 찾아 공유하므로 나머지 계정은 권한 오류를 받는다. 403 은 빨라서 성능이 좋아 보이는 가짜 숫자가 된다 |
| `stress` 와 `WS=1` 동시 사용 | VU 구간 통계가 WebSocket VU 까지 세어 계단이 밀린다 |
| `ALLOW_REAL_AI=1` | 실제 Gemini 쿼터가 소진되면 그때부터 전부 실패해서, 성능 대신 "쿼터가 언제 떨어지나"를 재게 된다 |
| 전/후 사이 설정 변경 | `VUS`·`DURATION`·`THINK_MS`·API 목록·계정 수를 바꾸면 그 차이는 성능 개선이 아니다 |

## 9. 알려진 제약

- **"AI 대기가 톰캣 스레드를 묶는가" 는 이 방식으로 재현되지 않는다.** AI 항목은 파이썬에 직접 붙어 스프링을 거치지 않는다. S3 로 측정되는 것은 파이썬 AI 서버의 처리 한계다. 스프링 쪽을 보려면 `POST /api/v1/support/chatbot/questions` 를 때려야 하는데 계정당 하루 10회 제한이 있어 부하 테스트가 성립하지 않는다
- 리포트의 "기준 통과" 배지는 요청 0건인 그룹도 통과로 센다
- 비교 페이지는 프로파일·API 수·계정 수·최대 VU 만 대조한다. `DURATION` 과 `THINK_MS` 차이는 잡지 못하므로 사람이 지켜야 한다
