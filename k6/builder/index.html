Pairing 부하 테스트 빌더

이 페이지는 테스트를 실행하지 않는다. 실행할 명령을 만들어 줄 뿐이다. 브라우저는 보안상 내 PC 의 프로그램(k6)을 실행할 수 없다.

1. 아래에서 대상·계정·API·부하를 고른다  →  2. 맨 아래 [명령 복사] 를 누른다  →  3. PowerShell 을 열고 Pairing-backend 폴더에서 붙여넣어 실행

폴더가 중요하다. 리포트를 k6/reports/ 에 상대경로로 저장하기 때문에, 다른 폴더에서 실행하면 테스트는 돌아도 마지막에 리포트 저장이 실패한다.

1대상 서버

배포된 dev 를 칠 때는 ALB 주소를 넣는다
AI 항목을 고를 때만 쓴다. 파이썬에 직접 붙는다
파이썬 .env 의 INTERNAL_API_KEY 와 같아야 한다

2테스트 계정

이 서비스는 로그인하면 그 계정의 이전 세션을 끊는다.
그래서 동시에 살아 있을 수 있는 세션 수 = 계정 수다. 계정 1개로 VU 50 을 돌려도 로그인은 setup 에서 한 번만 하므로 동작은 하지만, 50개 VU 가 같은 토큰·같은 사용자 데이터를 공유하게 된다. 계정 단위 캐시나 락이 있으면 실제와 다른 숫자가 나온다.

권장: VU 10명당 계정 1개, 최대 20개까지 (기본값 VU 150 이면 15개다). 비율을 더 높이면 테스트 계정을 수십 개 만들어야 해서 현실적이지 않고, 계정당 VU 10명이면 계정 단위 캐시·락의 영향을 판별하기에 충분하다.

역할이 필요한 API 를 고르면 그 역할 계정이 최소 1개는 있어야 한다.
비밀번호에 : 가 들어가면 이 형식으로 표현할 수 없다. 테스트 계정은 : 없는 비밀번호를 쓴다. 그리고 비밀번호를 틀리면 안 된다 — 실패가 IP 기준 20회를 넘으면 그 IP 가 2시간 차단된다.

3부하 시나리오

stress 는 이 값의 25/50/75/100/150% 를 차례로 밟는다. 150 이면 38 → 75 → 113 → 150 → 225명. ECS 1 vCPU 는 50~100 req/s 가 천장이고, 생각 시간 1초면 VU 하나가 약 0.83 req/s 를 만든다 — 즉 한계는 동시 60~150명 사이다. 계단이 그 구간을 가운데 두고 지나가도록 잡은 값이다.
stress 에서는 계단 하나를 유지하는 시간이다. 총 시간 = (증감+유지)×5 + 증감. 1 vCPU 로 묶으면 JIT·GC 안정화가 느려서 1분은 워밍업 중 수치를 재게 된다
VU 를 올리고 내리는 구간. 짧으면 순간 폭주가 되어 정상 부하가 아니다
반복 사이 대기. 0 이면 서버가 아니라 k6 한계를 재게 된다. 고른 API 개수에 맞춰야 한다 — 한 반복이 고른 API 를 전부 호출하므로, 개수가 늘면 같은 값이라도 부하가 그만큼 커진다. 사용자 1명이 초당 0.85건을 만드는 기준으로 1개 = 1000 / 4개 = 4500 / 6개 = 7000
리포트 파일명이 된다. before / after 로 두면 비교가 쉽다

4호출할 API

endpoints.js 에 없는 key 를 넣으면 k6 가 시작할 때 사용 가능한 목록을 보여주며 멈춘다

5WebSocket (선택)

동시 접속 수. 화면을 열어 둔 사용자의 절반쯤으로 잡는다 (목표 VU 150 기준)
기본값 13m 은 stress 전체 실행 시간이다 — 연결이 계단 내내 살아 있어야 브로커 부담이 드러난다. 비우면 DURATION(계단 하나) 과 같아져서 첫 계단에서 끊긴다
연결을 맺고 구독한 뒤 하트비트만 보내며 유지한다. 실제 사용자가 화면을 열어 둔 상태다. 스프링 태스크가 2대 이상이면 인스턴스 간 push 유실이 재현된다 — 브로커가 인메모리 SimpleBroker 라서 그렇다(StompWebSocketConfig 주석). 부하 테스트로 드러낼 수 있는 실제 문제다.

6합격 기준 (선택)

기준을 넘기면 k6 가 종료 코드 99 로 끝난다. AI 를 조회와 같은 기준으로 묶지 않는 이유는, AI 하나가 전체 p95 를 끌어올려서 조회 성능이 나빠져도 안 보이게 되기 때문이다.
