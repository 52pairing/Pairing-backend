# Pairing 부하 테스트 가이드

목표: **동시 접속을 계단식으로 올려 서비스가 무너지는 지점(한계점)을 찾고, 개선 전/후로 그 지점이 얼마나 올라갔는지 보여준다.**

- 대상: 로컬 스프링부트 (`localhost:8080`)
- AI(파이썬)는 **스텁**으로 두고 부하를 건다 — 실제 Gemini 는 쓰지 않는다
- 실행은 내 PC 에서, 결과는 HTML 파일로 남는다

---

## 0. 처음 한 번만

**k6 설치**

```
winget install k6
```

**설치 확인** — 버전이 나오면 준비 끝이다.

```
k6 version
```

## 1. 세 줄 요약

| 단계 | 무엇을 |
| --- | --- |
| 1 | `k6/builder/index.html` 을 더블클릭해서 열고, 설정을 고른 뒤 **[명령 복사]** |
| 2 | PowerShell 에서 `Pairing-backend` 폴더로 이동해 붙여넣기 |
| 3 | `k6/reports/<이름>.html` 을 열어 **한계점 표**를 본다 |

빌더는 **명령을 만들어 줄 뿐 테스트를 실행하지 않는다.** 브라우저는 보안상 내 PC 의 프로그램을 실행할 수 없다.

## 2. 기본값 — 그대로 쓰면 된다

빌더를 열면 한계점 찾기에 맞춰 이미 설정되어 있다.

| 항목 | 기본값 | 이유 |
| --- | --- | --- |
| 프로파일 | `stress` | 부하를 계단식으로 올려 무너지는 지점을 찾는다 |
| 목표 VU | `150` | **38 → 75 → 113 → 150 → 225명** 을 차례로 밟는다 |
| 유지 시간 | `2m` | 계단 하나를 유지하는 시간 |
| 증감 시간 | `30s` | 계단 사이를 올라가는 시간 |
| 생각 시간 | `1000ms` | 실제 사용자가 화면을 보는 시간 |
| API | 프론트 폴링 경로 6개 | 실제 트래픽에서 비중이 가장 큰 경로 |

**총 실행 시간은 약 13분**이다. `(30s + 2m) × 5 + 30s`

첫 계단(38명)은 사실상 워밍업이다. 수치가 나빠도 무시한다.

### 왜 150명인가 — 운영 환경이 ECS 1 vCPU 이기 때문이다

VU 는 가입자 수가 아니라 **동시 접속자 수**다. 그리고 몇 명까지 잡아야 하는지는 **운영 환경의 처리량**에서 나온다.

1 vCPU 는 1초에 1초치 CPU 만 쓴다. 조회 API 한 건이 CPU 를 8~15ms 쓴다고 보면 이론상 65~125 req/s, 여유를 두면 **50~100 req/s** 가 천장이다.

이걸 동시 접속자로 환산한다. 생각 시간 1초 + 응답 0.2초면 VU 하나가 1.2초에 한 건, 즉 **0.83 req/s** 를 만든다.

| ECS 처리량 | 필요한 동시 접속자 |
| --- | --- |
| 50 req/s | 약 60명 |
| 100 req/s | 약 120명 |

**한계는 동시 60~150명 사이**에 있다. 목표 VU 150 은 계단이 그 구간을 가운데 두고 지나가도록 잡은 값이다.

### 그래서 로컬 스프링을 1 vCPU 로 묶어야 한다

**이 항목이 없으면 위 숫자가 전부 무의미해진다.** 이 PC 는 코어가 여러 개라 150명을 여유롭게 받아낸다. 그렇게 찾은 한계는 ECS 가 아니라 **내 PC 의 한계**다.

```
./gradlew bootJar
```

```
$p = Start-Process java -ArgumentList '-Xmx768m','-XX:ActiveProcessorCount=1','-jar','build/libs/app.jar' -PassThru; $p.ProcessorAffinity = 1
```

| 옵션 | 하는 일 |
| --- | --- |
| `ProcessorAffinity = 1` | CPU 0 하나만 쓰게 묶는다 |
| `-XX:ActiveProcessorCount=1` | **JVM 이 스스로 1코어라고 인식하게** 한다. 없으면 GC 스레드 수를 실제 코어 수대로 잡아 ECS 와 다르게 동작한다 |
| `-Xmx768m` | 현재 ECS 에서 실제로 쓰는 힙 크기 (아래 참고) |

> PostgreSQL·Redis 는 묶지 않는다. ECS 도 RDS 를 별도 장비로 쓰므로 **묶지 않는 쪽이 실제와 가깝다.**

### 참고: ECS 힙이 768MB 로 돌고 있다

`Dockerfile` 에 힙 옵션이 없다. 그러면 JVM 이 **컨테이너 메모리의 25%** 만 힙으로 잡는다 — 3GB 를 줬는데 실제로는 768MB 만 쓰고 나머지 2GB 는 놀고 있다.

부하 중 GC 가 잦게 나오면 원인이 여기일 가능성이 높고, 그렇다면 **개선 전/후로 보여주기 좋은 항목**이다.

```
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=70", "-jar", "app.jar"]
```

같이 볼 만한 항목이 하나 더 있다. 톰캣 스레드 기본값이 200인데 1 vCPU 에서 200개는 컨텍스트 스위칭 낭비가 크다. 50으로 줄이는 것도 전/후 비교 후보다. (HikariCP 기본 10 은 1 vCPU 기준 적정하니 건드리지 않는다.)

## 3. 준비물

### 스프링부트 — 1 vCPU 로 묶어서 띄운다

2번의 `ProcessorAffinity` 방식으로 띄운다. **IDE 의 실행 버튼으로 띄우면 코어를 전부 쓰기 때문에 한계가 안 나온다.**

PostgreSQL 과 Redis 는 평소처럼 띄우면 된다.

```
docker compose up -d
```

### 테스트 계정

**이 서비스는 로그인하면 그 계정의 이전 세션을 끊는다.** 그래서 VU 여러 개가 한 계정을 공유하면 서로를 로그아웃시킬 수 있다. 스크립트는 `setup()` 에서 계정당 한 번만 로그인해 이 문제를 피하지만, 계정이 너무 적으면 모든 VU 가 같은 사용자 데이터를 보게 되어 캐시·락의 영향이 실제와 달라진다.

**권장: VU 10명당 계정 1개, 최대 20개.** 기본값 VU 150 이면 15개다.

역할이 필요한 API 를 고르면 그 역할 계정이 최소 1개는 있어야 한다.

> ⚠️ **비밀번호를 틀리면 안 된다.** 로그인 실패가 IP 기준 20회를 넘으면 그 IP 가 **2시간 차단**된다. 스크립트는 실패 3번이면 즉시 멈춘다.
>
> 비밀번호에 `:` 를 쓰면 안 된다. 계정 형식이 `이메일:비밀번호:역할` 이라 구분이 깨진다.

### 파이썬 AI 서버 (AI 경로를 함께 볼 때만)

Docker 로 띄우면 `.env` 를 자동으로 읽는다.

```
docker compose up -d --build
```

`.env` 에 스텁을 켜 둔다.

```
AI_STUB_MODE=true
AI_STUB_DELAY_MS=20000
AI_STUB_JITTER_MS=3000
```

`AI_STUB_DELAY_MS` 가 핵심 다이얼이다. **AI 응답을 기다리는 동안 톰캣 스레드가 묶이는 문제**를 이 값으로 재현한다.

```
cd C:\Users\user\Desktop\final-module\Pairing-backend
```

문제가 없으면 `stress` 로 되돌려 본 측정을 한다.

## 5. 결과 읽기 — 한계점 표

리포트를 열면 이 표가 가장 위에 있다.

```
동시접속   요청     p95        앞구간대비   실패율
    38명    3820     78.4ms          -    0.00%
    75명    7410    124.0ms       1.6배    0.00%
   113명   10680    268.2ms       2.2배    0.00%  ← 한계
   150명    3390      4.31s      16.1배    0.42%
   225명    2480      9.87s       2.3배    3.10%
```

**읽는 법**

- `앞 구간 대비` 가 갑자기 튀는 줄이 무릎이다. 위 예시는 75명까지 멀쩡하다가 113명에서 2.2배로 처음 꺾였고, 150명에서 완전히 무너졌다
- 판정 기준은 **지연 2배 이상** 또는 **실패율 1% 이상**, 둘 중 먼저 오는 쪽이다
- 요청 수가 줄어드는 것도 신호다. 느려지면 같은 시간에 처리하는 양이 줄어든다 — 위 표에서 113명이 10,680건인데 150명이 3,390건인 게 그 증거다

**이 서비스의 현재 한계는 동시 75명** 이라고 말하면 된다. 무릎으로 찍힌 113명은 *이미 꺾인* 지점이라, 안전하게 감당하는 수치는 그 앞 계단이다.

끝까지 안 무너지면 리포트가 알려준다 — 그때는 VU 를 올려서 다시 돌린다.

### 서버 쪽은 Grafana 로 본다

리포트의 숫자는 **클라이언트가 기다린 시간**이다. 왜 느려졌는지는 Grafana 의 스프링부트 성능 대시보드를 같은 시간대로 맞춰 봐야 한다.

| 볼 것 | 의미 |
| --- | --- |
| `tomcat_threads_busy` vs `config_max` | 스레드가 꽉 찼으면 그게 병목 |
| `hikaricp_connections_pending` | 0 을 넘으면 DB 커넥션 대기 |
| JVM 힙 · GC 시간 | 힙이 차서 GC 가 길어지는지 |

> 스프링을 CPU 0 에 묶어 뒀으므로, k6 가 **같은 코어를 뺏지 않는지** 확인한다. 작업 관리자에서 스프링(java) 이 CPU 0 을 100% 쓰고 있으면 정상이다. 반대로 지연이 늘었는데 java 가 한가하면 k6 나 PostgreSQL 쪽이 병목이니, 그때 나온 한계 수치는 ECS 이야기가 아니다.

## 6. 개선 전/후 비교

1. 개선 전에 `실행 이름` 을 `before` 로 두고 돌린다
2. 코드를 고친다
3. **설정을 하나도 바꾸지 말고** `after` 로 다시 돌린다
4. `k6/compare.html` 을 열어 `reports/before.json` 과 `reports/after.json` 을 넣는다

조건(VU·시간·API·계정 수)이 다르면 비교 페이지가 경고한다. 조건이 다르면 그 차이는 성능 개선이 아니라 조건 차이다.

**가장 설득력 있는 문장**은 이것이다.

> ECS 1 vCPU 기준으로, 개선 전에는 동시 75명에서 무너졌는데 개선 후에는 150명까지 버팁니다.

운영 환경 스펙을 앞에 붙이는 게 중요하다. 그래야 이 숫자가 "내 노트북에서 잰 값"이 아니라 **실제 서버 용량**으로 읽힌다.

`실행 이름` 이 같으면 리포트를 덮어쓴다. 여러 번 돌릴 때는 `before-1`, `before-2` 로 구분한다.

## 7. 시나리오별 목적

| 프로파일 | 언제 | 무엇을 보나 |
| --- | --- | --- |
| `smoke` | 설정 확인 | 계정·주소가 맞는지. 30초 |
| **`stress`** | **한계점 찾기** | **몇 명까지 버티는가 (기본값)** |
| `load` | 목표 부하 검증 | 정해둔 인원에서 기준을 지키는가 |
| `soak` | 장시간 안정성 | 메모리·커넥션 누수 |

### AI 경로를 볼 때

목적이 처리량이 아니라 **"AI 대기 중에 다른 API 가 같이 느려지는가"** 다.

- AI 항목은 **파이썬에 직접** 붙는다 (스프링 쿼터가 막아서 스프링 경유로는 부하를 못 건다)
- 챗봇은 호출 1회에 스텁이 **2번** 돈다(관련성 임베딩 + 답변 생성). 지연 값을 2배로 계산한다
- `AI_STUB_DELAY_MS` 를 3000 → 20000 → 60000 으로 올려가며, 조회 API 의 p95 가 얼마나 나빠지는지 본다

## 8. 자주 막히는 곳

| 증상 | 원인과 해결 |
| --- | --- |
| 리포트가 저장 안 됨 | `Pairing-backend` 폴더에서 실행해야 한다 |
| 로그인 실패로 중단 | 계정·비밀번호·역할 확인. **틀린 채로 재시도하면 IP 가 2시간 막힌다** |
| 특정 API 가 제외됨 | 그 API 가 필요로 하는 데이터(채팅방·협상 등)가 없다. 리포트의 "제외된 항목"에 이유가 나온다 |
| `역할 계정이 없다` | CLIENT/FREELANCER 전용 API 를 골랐는데 해당 역할 계정이 없다 |
| AI 가 스텁이 아니라고 멈춤 | 파이썬을 `AI_STUB_MODE=true` 로 다시 띄운다. 확인: `curl localhost:8000/metrics \| grep gemini_stub_mode` |
| 빌더에 API 목록이 안 보임 | `k6 run k6/tools/dump-catalog.js` 로 목록을 다시 만든다 |

## 9. API 를 추가할 때

1. `k6/endpoints.js` 에 항목 추가
2. 빌더용 목록 재생성

```
k6 run k6/tools/dump-catalog.js
```

3. 검사

```
node k6/tools/check-catalog.mjs
```

경로에 오타가 있으면 404 를 받는데, **404 는 DB 를 안 타서 아주 빠르다.** 그러면 성능이 좋아진 것처럼 보인다. 그래서 CI 가 이 검사를 자동으로 돌린다.
