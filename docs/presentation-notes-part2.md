# 발표 노트 — 2번 파트 (도메인)

> 담당 도메인: 리뷰 · 등급 · 마이페이지 · 이력서 · 결제수단 · 1:1문의 · 챗봇 · 알림 · 홈
> 용도: PPT·발표 대본 재료를 개발하면서 쌓아두는 곳. 완성된 문서가 아니라 **재료 창고**다.
> 최초 작성: 2026-08-12

## 이 문서 쓰는 법

- 개발하다 "이거 발표 때 쓰겠는데" 싶으면 **그 자리에서** 해당 항목에 3줄 적는다. 나중에 기억 안 난다.
- 각 항목은 `상황 → 판단 → 결과` 3단으로 적는다. 발표는 이 형식이면 그대로 읽힌다.
- **숫자를 남긴다.** "빨라졌다"가 아니라 "12/12 정확", "500 → 400". 심사위원은 숫자를 본다.
- `⬜` 는 아직 안 채운 것, `✅` 는 발표에 바로 쓸 수 있는 것.
- 커밋 해시·PR 번호·파일 경로를 같이 적어두면 발표 때 근거로 띄울 수 있다.

# 1. 고객 · 문제 · 기능

## 1-1. 고객 정의 — 내 도메인 관점

⬜ **사용자가 내 화면을 만나는 순간이 언제인지** 적기. (마이페이지·리뷰·문의는 "가입 직후"가 아니라 "일이 끝난 뒤" 만나는 화면이다 — 이게 설계를 갈랐다면 그 얘기가 소재)

| 화면 | 누가 | 언제 만나는가 |
|---|---|---|
| 이력서 | 프리랜서 | 가입 직후 / 매칭 안 될 때 고치러 |
| 마이페이지 | 양쪽 | 계약 전 상대 확인, 정산 전 결제수단 등록 |
| 리뷰 | 양쪽 | **대금 지급이 끝난 뒤** |
| 1:1 문의·챗봇 | 양쪽 | 막혔을 때 (= 이탈 직전) |
| 알림 | 양쪽 | 서비스 밖에 있을 때 다시 불러오는 통로 |

⬜ 확인 방법 (인터뷰/설문/본인 경험 중 뭐였는지)

## 1-2. 문제 정의

⬜ 내 도메인이 푸는 문제 한 줄씩

- **챗봇**: 사용자가 막혔을 때 FAQ를 읽는 게 아니라 **그 화면으로 가고 싶어 한다**. 답변만 주는 챗봇은 절반만 푼다. → 답변 + 이동 버튼
- **리뷰**: 언제 리뷰를 열어줄지가 곧 신뢰도다. 너무 일찍 열면 거래 안 끝난 사람이 감정으로 쓴다.
- ⬜ 마이페이지 / 이력서 / 결제수단 / 알림

⬜ 기존 대안 (크몽·위시켓 등은 이 지점을 어떻게 하고 있는지 — 조사해서 적기)

## 1-3. 실제 제작한 기능

### 백엔드 — 구현한 API·도메인

✅ 발표에 그대로 쓸 수 있는 표

| 도메인 | 핵심 기능 |

### 데이터 모델 — 발표용 포인트

✅ **작성자 스냅샷 (`inquiry.writer_name`, `writer_role`, `writer_email`)**
- 상황: 문의 목록을 관리자가 볼 때 `account` 를 조인하면 N+1이고, 탈퇴하면 작성자가 사라진다
- 판단: 작성 시점 값을 문의에 **복사해서 박았다** (역정규화)
- 결과: 조인 없이 목록 조회, 탈퇴 후에도 이력 보존
- → 3-2 "정규화/역정규화 판단" 항목에 그대로 들어감

✅ **`CdnMappable` — object key 만 저장하고 URL은 응답 시점에 조립**
- 상황: 파일 URL을 DB에 통째로 저장하면 CDN 도메인이 바뀔 때 전 레코드를 갱신해야 한다
- 판단: DB엔 상대 경로(object key)만. `~Url` 로 끝나는 필드를 직렬화 시점에 자동 변환하는 마커 인터페이스
- 결과: `S3_CDN_URL` 환경변수만 바꾸면 전환 끝, 데이터 무수정

⬜ ERD 핵심 관계 (account ↔ resume ↔ file, contract ↔ review) 캡처 준비

### 제외한 기능과 이유

✅ 이력서 PDF 내보내기 — 기간 대비 가치가 낮다고 판단해 삭제 (커밋 이력 있음)

# 3. 직면한 문제와 해결

> **여기가 발표의 핵심이다.** 2~3개를 깊게 파는 게 요구사항이므로,
> 아래 후보 중 가장 이야기가 되는 것을 골라 나머지는 한 줄로 줄인다.

## ⭐ 후보 A — 배포 환경에서만 나는 500, 원인은 DB CHECK 제약

**발표 가치: 상**. 증상→가설→배제→확정 흐름이 깔끔하고, 로그·SQL 근거가 다 남아 있다.

### 상황
- 1:1 문의에서 **파일을 첨부하면** `500 GLOBAL_001`, 파일 없으면 정상 등록
- 로컬에서는 재현 안 됨. 배포 환경에서만 발생
- traceId `4976601d`

### 가설을 하나씩 배제한 과정 (← 발표용 표)

| 가설 | 나왔어야 할 응답 | 판정 |
|---|---|---|
| 파일 용량 10MB 초과 | `400 FI_003` | ❌ |
| 확장자 위반 | `400 GLOBAL_008` | ❌ |
| S3 업로드 실패 | `500 GLOBAL_007` | ❌ |
| DB 컬럼 누락 | SQL 예외 | ❌ (서버 DB는 정상) |
| **그 외 잡히지 않은 예외** | `500 GLOBAL_001` | ✅ |

> 핵심: **에러 코드를 도메인별로 나눠둔 덕에 "무엇이 아닌지"를 코드만 읽고 배제할 수 있었다.**
> `GLOBAL_001` 은 catch-all 이라는 사실 자체가 결정적 단서였다.

### 진짜 원인
```
PSQLException: new row for relation "file"
violates check constraint "file_file_group_check"
```
- Hibernate 6은 `@Enumerated(EnumType.STRING)` 컬럼에 **CHECK 제약을 자동 생성**한다
- `ddl-auto: update` 는 컬럼은 추가해도 **기존 CHECK 제약은 절대 갱신하지 않는다**
- `FilePurpose` 에 `INQUIRY_ATTACHMENT` 를 나중에 추가했는데, DB의 CHECK은 옛 목록 그대로였다
- → enum에 값을 추가하는 순간 배포 환경에 시한폭탄이 생기는 구조

### 조치
1. 즉시 조치 — 해당 제약 재생성
2. **재발 방지 — 전수 조사**: 엔티티 37개에서 `EnumType.STRING` 컬럼 62개를 추출하고, `pg_constraint` 덤프와 대조하는 스크립트를 짰다
   - 결과: **`settlement.status` 에 `CANCELED` 누락 1건 추가 발견** (아직 아무도 프로젝트 취소를 안 해봐서 안 터진 상태였다)
3. 코드 조치 — 예외 처리 표준화 (아래 후보 B)

### 발표 한 줄
> "장애 하나를 고치는 데서 끝내지 않고, **같은 원인이 숨어 있는 곳을 전부 찾는 스크립트**를 짰다. 한 건을 더 찾았다."

**남길 것**: Grafana 로그 스크린샷, 대조 스크립트, before/after 제약 정의

## ⭐ 후보 B — 에러 응답 표준화: 잘못된 요청이 500으로 나가던 문제

**발표 가치: 중상**. A의 후속이라 이어서 말하기 좋다.

### 상황
전역 예외 핸들러가 `BusinessException` 과 검증 예외만 잡고 있었다. 나머지는 전부 `Exception.class` catch-all → **`500 GLOBAL_001`**.

그래서 아래가 전부 500으로 나갔다.

| 실제 원인 | 올바른 응답 | 당시 응답 |
|---|---|---|
| multipart part 이름 오타 | 400 | 500 |
| Content-Type 이 multipart 아님 | 415 | 500 |
| 업로드 상한 초과 | 413 | 500 |
| UNIQUE 중복 | 409 | 500 |
| CHECK 위반 (후보 A) | 500 | 500 (구분 불가) |

### 판단
- **500은 "서버 잘못"이라는 뜻이다.** 프론트 요청이 틀렸는데 500을 주면 프론트는 백엔드 장애로 읽고 원인을 엉뚱한 데서 찾는다
- `DataIntegrityViolationException` 은 한 덩어리가 아니라 **SQLState 로 갈라야 한다**
  - `23505`(중복) / `23503`(FK) → **409**, `warn` — 사용자가 요청을 바꾸면 풀린다
  - `23514`(CHECK) / `23502`(NOT NULL) → **500**, `error` + 스택 전체 — 사용자가 손댈 수 없는 스키마 문제

### 결과
- `GLOBAL_012` ~ `GLOBAL_015` 신설, 핸들러 2개 추가
- 같은 장애가 재발하면 `GLOBAL_001` 이 아니라 `GLOBAL_013` 으로 뜨고 **로그에 위반한 제약 이름이 남는다**

### 발표 한 줄
> "에러 코드는 사용자를 위한 게 아니라 **다음에 디버깅할 사람을 위한 것**이다."

**남길 것**: `CommonExceptionAdvice` before/after, 에러 코드 표

## ⭐ 후보 C — 챗봇을 "답변"에서 "행동"으로: intent 기반 이동 버튼

**발표 가치: 상 (AI 파트 3-4에 그대로 대응)**

### 문제
FAQ 챗봇이 "이력서는 마이페이지에서 수정하실 수 있습니다"라고 답해도, 사용자는 **그 페이지를 다시 찾아가야 한다.** 답변은 맞는데 문제는 안 풀린다.

### 설계 판단 — LLM에게 URL을 만들게 하지 않는다
- LLM에 경로를 생성시키면 **없는 URL을 지어낸다**(환각). 라우팅이 바뀌면 조용히 깨진다
- 그래서 LLM은 **닫힌 목록에서 코드 하나만 고르게** 했다. 코드→경로 변환은 서버가 한다

```
LLM  →  intent 코드 (9개 중 1개)  →  Spring 이 경로로 변환  →  버튼
```

- 강제 수단: Gemini `response_schema` 의 `enum` 으로 값을 닫음
- 2차 방어: 그래도 목록 밖 값이 오면 서버에서 `NONE` 으로 떨어뜨림 → **최악이라도 버튼만 안 나오고 답변은 정상**
- 역할 필터: 프리랜서에게 "프로젝트 등록" 버튼이 뜨면 안 되므로, **서버가 계정 role 로 걸러낸다.** LLM은 역할을 모른다

### intent 목록 (9종)
`RESUME_EDIT` / `PROJECT_CREATE` / `PAYMENT_METHOD` / `SETTLEMENTS` / `MY_PROJECTS` / `NEGOTIATION_LIST` / `CONTRACTS` / `INQUIRY_NEW` / `NONE`

### 검증 — 숫자가 있다
- 실제 모델(`gemini-3.6-flash`)로 질문 12개 테스트
- 1차 결과 **10/12**. 오분류 2건:
  - "오늘 날씨 어때?" → `INQUIRY_NEW` (서비스와 무관한데 1:1 문의를 권함)
  - "500만원 제안해줘" → `INQUIRY_NEW` (협상 화면으로 보냈어야 함)
- 프롬프트 가이드 수정: `INQUIRY_NEW` 는 **"서비스 관련 질문인데 답할 수 없을 때만"** 으로 좁히고, `NONE` 에 "날씨·상식 등 서비스 무관" 을 명시
- 재테스트 **12/12**, 기존 6건 회귀 없음

### 발표 한 줄
> "AI가 틀릴 수 있는 부분을 **AI에게 맡기지 않는 구조**로 바꿨다. LLM은 분류만 하고, 경로와 권한은 서버가 정한다."

## 후보 D-1 — 알림을 "안 보내기로" 한 판단 (수수료 청구)

**발표 가치: 중**. 기능을 더한 이야기가 아니라 **덜어낸 이야기**라 오히려 눈에 띈다.

수수료 청구는 4경로다. 처음엔 4개 다 알림을 붙이려다, **사용자가 그때 어디에 있는지**를 기준으로 다시 봤다.

| 수수료 | 납부자 | 청구 시점 | 그때 사용자는 | 결정 |
|---|---|---|---|---|
| 착수금 | 클라이언트 | 프로젝트 등록 시 | **그 화면에 있음** | ❌ 안 보냄 |
| 착수금 | 프리랜서 | 계약 체결 시 | 서명 직후 이탈 가능 | ⚠️ 체결 알림 문구에 합침 |
| 성공보수 | 클라이언트 | 프로젝트 완료 | **서비스 밖** | ✅ 보냄 |
| 성공보수 | 프리랜서 | 프로젝트 완료 | **서비스 밖** | ✅ 보냄 |

- 방금 본인이 한 행동을 다시 알려주는 알림은 **노이즈**다
- 같은 시점에 알림 2개가 연달아 가면 둘 다 안 읽는다 → 하나로 합쳤다
- 문구도 갈랐다: `closesProject()` 상 **프로젝트를 종료시키는 건 클라이언트 성공보수뿐**이라,
  프리랜서에게 "결제하면 평가를 쓸 수 있다"고 하면 **사실과 다르다**

**기한 안내도 뺐다.** `dueDate` 가 채워지지 않고 연체 전환 스케줄러도 없어서,
"언제까지"를 쓰면 **지킬 수 없는 약속**이 된다. 연체는 명세에 없어 범위에서 제외했다.

> 발표 한 줄: *"알림은 많이 보낼수록 안 읽힌다. 4개 중 2개만 보내기로 했다."*

## 후보 E — 외부 AI 서버 장애 대응 (서킷 브레이커)

⬜ 살 붙이기

- 챗봇 답변은 Python AI 서버 경유. **AI 서버가 죽으면 챗봇 화면 전체가 죽는다**
- Resilience4j `@CircuitBreaker(name="pythonChatbotApi", fallbackMethod="askFallback")`

- ⬜ 실제로 AI 서버를 내려서 폴백 동작을 확인한 기록 남기기 (테스트하면 발표 근거가 됨)

## 후보 F — 도메인 용어·단위 불일치 (3-3 에 대응)

⬜ 살 붙이기

✅ 실제 있었던 것
- **금액 단위**: API는 원 단위, 화면은 만원 단위. 와이어프레임이 원 단위로 그려져 있어 정정. 도메인에서 만원 단위 검증(`AMOUNT_UNIT = 10_000`)까지 추가
- **등급 명칭**: 와이어프레임에 프리랜서 등급이 골드/다이아로 그려져 있었는데, 실제 정책은 프리랜서 JUNIOR/SENIOR/MASTER · 클라이언트 SILVER/GOLD/DIAMOND. **와이어프레임이 틀린 케이스**
- **"계약 완료"의 의미**: 서명 완료인지 대금 지급 완료인지 팀 안에서 달랐다 → 리뷰 자격 판정의 기준 자체가 흔들렸다
- 발표 포인트: *"같은 단어를 서로 다르게 쓰고 있다는 걸 발견하는 게, 코드를 고치는 것보다 먼저였다"*

## 후보 G — 로컬 DB와 배포 DB가 다른 문제

⬜ 살 붙이기 (후보 A와 묶어도 됨)

- `db/init/*.sql` 로 만든 테이블은 **소유자가 `postgres`**, 앱 계정은 소유자가 아니라 `ALTER` 가 거부된다
  - 로그에 `오류: <table> 테이블의 소유주여야만 합니다` 가 경고로만 찍히고 **기동은 성공한다** → 조용히 스키마가 어긋난다
- 반면 Hibernate가 만든 테이블은 앱 계정 소유라 자동 갱신된다
- 결과적으로 **테이블마다 스키마 관리 주체가 달라졌다**
- 교훈: `ddl-auto: update` 는 스키마 관리 도구가 아니다. 마이그레이션 도구(Flyway 등)를 처음부터 썼어야 한다 → **"지금 다시 한다면" 항목에 그대로 쓸 수 있음**

### ⚠️ 이날의 판단 착오 — 발표에 쓸 수 있는 소재

`SETTLEMENT_DUE` 를 붙일 수 있게 되자 **정산 도메인 파일을 직접 고쳐서 연결했다가 되돌렸다.**

- 알림은 내 도메인이지만 **"언제 알림을 만들지"를 정하는 건 그 도메인의 책임**이다

  **그 도메인 담당이 자기 코드에 뭐가 들어갔는지 모른다**
- 앞서 협상·계약 알림은 요청만 했으면서 정산만 직접 고친 건 일관성도 없었다
- 교훈: *도메인 단위 분담에서 경계를 넘는 판단은 빠른 게 아니라 위험한 것이다.
  기다리는 게 답답해도 요청이 맞다.*
